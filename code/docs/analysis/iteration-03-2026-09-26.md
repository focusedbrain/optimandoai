# Iteration 03 — 2026-09-26

This iteration continues from `docs/analysis/iteration-02-2026-09-26.md`. It decides the reachability question WRC contract v2.0 §10 left to the test-backend step, and builds the local WR Code test backend that Milestone 2 planned. The code tip is `ca181c45` on `integration/consolidated-current`.

## Decision applied

The Author asked for the option that is most user-friendly and most secure, and accepted the recommendation on 2026-09-26: **a built-in test registry behind the transport seam, compiled only into explicit test builds, plus release trust pinned in source.**

- **The dev-only address allowance was rejected.** A local HTTPS server would need three exceptions in the hardened client (the loopback and private-address block, the certificate check, and the system DNS resolver), each a switch a release build could be misconfigured with. It also needs a server, certificates and environment variables on every machine.
- **The in-process registry needs none of that.** Everything above the transport seam runs unchanged: decoders, signatures, Merkle proofs, directory verification and all six gates.
- **The real network path** (TLS, DNS, HTTP) stays covered by the hardening tests. Later, a public staging instance of the WRC service can exercise it without any client exception.

## What changed (`ca181c45`)

| Piece | Change |
|---|---|
| Build flavor | `__WRC_BUILD_FLAVOR__` (`vite.config.ts`, main and renderer): `release` by default, `wrc-test` only from `pnpm run build:wrc-test`. `wrc/wrcBuildFlavor.ts` reads it; a bundle with any other value is `release`, and only an unbundled run (vitest) is `dev`. |
| Release trust | `wrc/wrcTrustAnchors.ts` holds the pinned registry, ingest and directory-operator anchors (null until the production WRC service exists, so a release build fails closed). A release build reads nothing else: the `WRDESK_WRC_*` trust variables are honored only in unbundled dev runs, and a pinned anchor with a `test-` key id is refused. This closes the gap found while deciding: before, launching the app with a doctored environment could point it at a foreign registry. |
| Test registry | `wrc/wrcTestRegistry.ts`: six seeded test publishers (`TEST01`–`TEST06`, domains under `.test`, every key id `test-`), with catalogs, envelopes, Merkle proofs, dual-signed directory records, manifests and `_wr` answers. Answers are served as JSON within the wire caps. The signed-in SSO domain is registered, live and with its own DNS proof, for the own publisher `TEST02`. There are 19 test codes, covering every class and namespace status, plus unknown, expired, suspended, retired, not-for-you, one-time and typo cases. |
| Containment | Release builds alias the registry to `wrcTestRegistry.release-stub.ts`. `scripts/verify-wrc-build-flavor.cjs` runs after `vite build` in all six build chains and fails a release bundle containing the registry, or a test bundle missing it. |
| Separate state | A test build uses `wrc-security.wrc-test.db` and `wrc-resolved-publishers.wrc-test.json`, so test floors and uses never touch real ones. |
| Side-by-side builds | The test build packages into `C:\build-output\build007-wrc-test` (Linux: `dist/release-wrc-test`), and cleanup keeps both folders. |
| Marking | A non-dismissible banner on every screen of a test build; `[WRC] TEST REGISTRY ACTIVE` in the main log; `wrc.runtimeStatus` reports the flavor for the coming WR Code surfaces. |
| Code sheet | `docs/operational/wrc-test-build.md`: how to build and run, who you are in the test build, all 19 codes with their expected outcome, and how to start over. |
