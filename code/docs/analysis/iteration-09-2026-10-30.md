# Iteration 09 — 2026-10-30

This iteration continues from `docs/analysis/iteration-08-2026-10-30.md`. It ends the coordination WebSocket reconnect loop seen on the test host after the switch to the public relay. The code tip is `ddb0067a` on `integration/consolidated-current`.

## Finding: the client evicted itself from the relay

- The relay keeps one WebSocket per (user, device) and terminates the older one when a second connection arrives (`packages/coordination-service/src/wsManager.ts`, `handleConnection`).
- The client opened a second socket whenever a caller found it not connected. `ensureSenderCoordinationWsForDeliveryAck` in `handshake/outboundQueue.ts` calls `connect()` when `isConnected()` is false — also while the first socket is still opening or a reconnect is pending.
- The evicted socket's `close` handler then set the shared `ws` reference (which by now pointed at the new socket) to `null` and scheduled another connect; that connect evicted the other socket in turn. The loop ran at the 1 s reconnect delay indefinitely. The build010 host log shows 3,331 `connect_begin` and the same number of `connect_open`, and never a close, because close was not logged.
- On the relay, the replaced socket's `close` removed the client entry by key — the new connection's entry. Until the device reconnected, live push missed it and capsules stayed queued.

## What changed (`ddb0067a`)

| Area | Change |
|---|---|
| Client (`p2p/coordinationWs.ts`) | `connect()` returns while a socket is open or opening (checked again after the token await) and cancels a pending reconnect timer instead of racing it. Each socket's handlers act only for that socket: a replaced socket's late close logs `close_stale_socket` and changes nothing. `close` logs code and reason; a close before open rejects the connect promise. |
| Relay (`coordination-service/src/wsManager.ts`) | Only the registered socket may deregister its (user, device) key. |
